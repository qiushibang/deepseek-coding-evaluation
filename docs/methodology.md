# 从真实项目到可比较的评测

## 先固定任务和完成条件

选择自己熟悉的项目，找出六个可独立说明的功能或缺陷，分别还原修改前的起点。不要把已有答案、目标提交或不必要的历史交给做题模型。题面要清楚说明用户希望发生什么、哪些边界必须保持、怎样才算完成。

由单独的出题代理编写测试，并在修改前基线和参考实现上校准。应提前固定题面、环境与验收版本，确认基线暴露问题、正确实现通过测试。测试不得把题面没要求的实现细节当成必选答案。

## 使用尽量一致的执行环境

本次使用 Pi Coding Agent 1.1.0，提供 Read（读取文件）、Write（写入文件）、Edit（编辑代码）、Bash（终端执行）四个工具。每个模型每题使用新会话和独立工作区，不读取其他模型答案。模型通过各自服务接口接入，工具框架相同并不意味着服务、配置或模型条件完全相同。

流程是：**固定基线与题面 → 独立运行 → 封存答案 → 独立验收 → 汇总数据**。模型运行期间可自行检查和修改代码；结束后不向模型泄露隐藏测试，再指导它修补答案。

## 让验收与做题隔离

封存代码之后，独立运行隐藏测试和原有回归测试，同时检查是否存在绕过验收的行为。自称“完成”不能代替验收结果。测试程序失败也不自动等于模型任务失败：先区分业务实现错误、环境错误和测试夹具错误。

历史实验中存在题面与测试校准。因此公开结果采用当时确定的有效题面和验收口径，并保留这一限制，不能宣称所有标准都在首次运行前完全冻结。校准应独立检查已封存的答案，不给模型额外反馈修改机会；未来正式实验应在开跑前完成校准并登记版本。

## 记录与解释

核心指标为效果、时间和成本，辅以工具调用、词元消耗和输入缓存命中率。每题结果、有效用量、排除的环境异常和数据缺口都应分别记录。失联或中断造成的未知花费应保持未知，不能填零。

本次四模型各六题的有效记录共 24 条。每题只做一次有效采样，不能用来估计稳定成功率或统计显著性。服务平台、题面版本和缓存范围存在差异，也不能称为完全控制变量的实验。

## 模型变强之后

当简单题都能通过，应增加跨模块改动、并发与异常恢复；加入多轮需求澄清、长上下文和更多工具选择；重复运行，观察成功率波动。新标准提前定义，比较相同预算下的完成率、耗时和成本。

本仓库公开的是方法介绍、整理后的历史指标和演示网站，不包含完成原项目重跑所需的全部源代码与测试。可使用[题目模板](../templates/task-template.md)在自己的项目中重新设计一轮实验。
